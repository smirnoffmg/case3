### Оценка и отчеты (15 + 15 + 25 баллов)

- [ ] Зафиксировать **proxy** Execution Accuracy (нормализация SQL) и честно описать ограничение (нет выполнения на БД) в отчете
- [ ] Сгенерировать **Markdown-отчет** для жюри: accuracy, approval rate, mean iterations, risk delta по итерациям
- [ ] Таблица **precision/recall судьи по классам** (static и hybrid)
- [ ] Матрица покрытия: 9 классов x детектор (static / LLM)

### Итеративный цикл (25 баллов)

- [ ] Подготовить **2-3 кейса** с 2+ итерациями (плохой SQL -> замечания -> исправление), сохранить `audit_log`
- [ ] Прогон pipeline на реальной LLM на задачах, где ожидается отказ на 1-й итерации
- [ ] Метрика в eval: **повтор `vuln_class`** между итерациями (regression rate)
- [ ] Метрика в eval: доля прогонов с **снижением risk** от 1-й к последней итерации
- [ ] (Опционально) Проброс флага регрессии из memory в repair-промпт

### Архитектура (10 баллов)

- [ ] ADR 0002: система не исполняет SQL (только генерация + аудит)
- [ ] ADR 0003: гибридный судья (static first, LLM optional)
- [ ] ADR 0004: critique memory и политика одобрения (risk <= 4, block >= 8)
- [ ] ADR 0005: prompt + RAG (BM25), без fine-tuning в MVP
- [ ] Краткий раздел в README или `doc/ARCHITECTURE.md`: альтернативы и почему отклонены

### Прозрачность и воспроизводимость (10 + 10)

- [ ] 1-2 примера «задача -> audit_log -> финальный SQL» в `doc/` или README
- [ ] Пояснение порога одобрения в тексте audit log (для аналитика)
- [ ] Файл `.env.example` с переменными из [README](README.md#настройки)
