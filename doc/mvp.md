# План реализации. Система генерации и аудита SQL

## Что мы делаем

Наша программа работает так: человек пишет задачу обычным текстом, программа создает SQL-запрос для PostgreSQL, проверяет его на уязвимости, сама исправляет проблемы и в конце выдает безопасный запрос вместе с логом проверки.

Программа не запускает запрос на базе, только готовит его. Цикл проверки и исправления заканчивается, когда **судья** одобрил запрос
или когда закончился лимит попыток.

## Из чего состоит программа

Это один процесс на Python. Внутри него работают такие части:

- **оркестратор**. Управляет циклом генерация, проверка, исправление.
- **генератор**. Создает SQL-запрос по тексту задачи.
- **судья**. Проверяет запрос на уязвимости. Состоит из двух частей: проверки по правилам на дереве запроса и проверки через модель.
- **память**. Копит все найденные проблемы, чтобы генератор не повторял одни и те же ошибки.
- **сервис схемы**. Хранит структуру базы и помогает находить нужные таблицы.
- **стенд оценки качества**. Считает метрики по тестовому набору данных.
- **интерфейс на Streamlit**. Через него человек вводит задачу и видит результат.

## Порядок работ

### Шаг 1. Каркас и контракты

1) Создаем структуру репозитория и файл pyproject.toml.
2) Берем готовые классы данных из baseline и не меняем их.
3) Делаем клиент для работы с моделью так, чтобы модель можно было заменить без переписывания кода. Сначала заглушка, потом одна
рабочая версия.

### Шаг 2. Сервис схемы

1) Пишем разбор файла data_model.sql в формат JSON.
2) Строим граф связей между таблицами.
3) Помечаем поля с личными данными людей, например имя, телефон, почту, дату рождения.
4) Делаем поиск таблиц, которые подходят под конкретную задачу.

### Шаг 3. Тестовый набор данных

1) Сами составляем пары "задача и SQL-запрос".
2) Часть пар безопасные и правильные. Часть пар содержит типовые уязвимости. Цель не меньше 50 пар, это дает дополнительные баллы.

### Шаг 4. Генератор

1) Пишем создание SQL-запроса по тексту задачи.
2) Делаем сборку подсказок для модели. Подсказка для первой попытки и подсказка для исправления это разные тексты.

### Шаг 5. Судья

1) Сначала пишем проверки по правилам. Они работают на дереве запроса и ловят понятные случаи: выборка всех полей, удаление или изменение
строк без условия, отсутствие лимита, опасные конструкции.
2) Потом добавляем проверку через модель. Она ловит сложные случаи по смыслу и пишет понятные пояснения.

### Шаг 6. Цикл и память замечаний

1) Собираем цикл: генератор создает запрос, судья проверяет, генератор исправляет. Все найденные замечания копятся и передаются
генератору на каждой следующей попытке. Если старая ошибка появилась снова, это считается ухудшением.

2) Добавляем лимит попыток и ограничение по времени 60 секунд.

### Шаг 7. Лог аудита

1) Пишем понятный отчет для человека. В отчете видно: какие риски нашли, сколько было попыток, почему итоговый запрос признали безопасным.

### Шаг 8. Стенд оценки качества

1) Делаем прогон по тестовому набору данных.
2) Считаем точность генерации, качество работы судьи, среднее число попыток, как снижается риск от попытки к попытке.

### Шаг 9. Интерфейс

1) Делаем интерфейс на Streamlit. Человек вводит задачу, программа работает сама, на выходе итоговый SQL-запрос и лог проверки.

### Шаг 10. Дополнительно, если останется время

1) Проверка запроса через план выполнения на локальной базе, запрос при этом не выполняется.
2) Поддержка хранимых процедур на языке PL/pgSQL.
