# 4. Политика одобрения и FeedbackMemory

Date: 2026-05-20

## Status

Accepted

## Context

После каждой итерации аудита нужно решить: одобрить SQL или отправить на
доработку. И — если на доработку — как передать генератору замечания так,
чтобы он не повторял те же ошибки в следующей итерации.

Два независимых решения, тесно связанных:

1. **Критерий одобрения.** Простая сумма рисков не работает: пять
   мелких находок (NO_PAGINATION × 5) дают сумму больше, чем одна
   SQL-инъекция; одобрять «много слабых лучше одной критической» —
   неверно.
2. **Передача замечаний.** Если каждой итерации заново скармливать полный
   список вулнов, генератор тратит токены и LLM путается. Если давать
   только последнюю — забываем уроки прошлых итераций (могут вернуться).

## Decision

**Two-tier подход к одобрению** (`judge/policy.py`, `contracts.is_approved`):

- `risk_threshold = 4.0` — максимальный итоговый риск среди всех находок.
- `hard_block_risk = 8.0` — любая отдельная находка с риском ≥ 8.0
  блокирует запрос независимо от threshold.
- `overall_risk = max(f.risk_score for f in findings)`. **Не сумма** —
  добавление мелких находок не меняет вердикт.

Одобрено ⇔ `max_risk ≤ 4.0` **И** ни одной находки с риском ≥ 8.0.

**FeedbackMemory** (`memory/feedback.py`) накапливает уроки между
итерациями:

- `add(audit)` сохраняет описания и рекомендации по найденным классам.
- `detect_regression(audit)` помечает классы, которые исчезли в прошлой
  итерации и вернулись — генератор получает их с пометкой
  «THIS IS A REPEAT MISTAKE».
- `is_stuck(min_iterations=2)` возвращает True, если два прохода подряд
  дали одинаковый набор классов — оркестратор выходит из цикла с флагом
  `stuck`, чтобы не сжигать оставшиеся итерации впустую.

## Alternatives considered

- **Сумма рисков.** Отклонено: см. выше.
- **Веса по классам с линейной агрегацией.** Отклонено: добавляет
  гиперпараметр без явной выгоды; max-risk даёт тот же результат проще.
- **Передавать в промпт полный JSON всех итераций.** Отклонено: на
  3-й итерации это уже 4–6 КБ контекста; LLM хуже фокусируется.
- **Хранить state в генераторе.** Отклонено: ломает контракт
  `SQLGenerator` (он stateless по дизайну); вся память — в оркестраторе.

## Consequences

- Любое будущее правило аудита, дающее риск ≥ 8.0, автоматически становится
  hard-block без правок в политике.
- `risk_threshold` настраивается через `.env` (`RISK_THRESHOLD`), что
  позволяет в продакшене ужесточить вердикт без правок кода.
- `FeedbackMemory` живёт только в пределах одного `run` —
  межпользовательской утечки уроков нет.
- Поскольку решение строится на max, а не на полном наборе, audit-лог
  должен явно показывать пороги: `final_risk = 3.0 ≤ 4.0 AND no hard-block`
  (это формируется в `audit/log_builder.py`).
