# 2. Система не исполняет SQL: только генерация и аудит

Date: 2026-05-20

## Status

Accepted

## Context

Кейс требует превращать естественно-языковые запросы в SQL для PostgreSQL и
гарантировать, что результирующий запрос безопасен. Один из вариантов
архитектуры — добавить read-only sandbox-исполнение, чтобы оценивать запросы
по реальному результату (Execution Accuracy на живой БД).

Это расширяет поверхность атаки: даже SELECT может вызвать DoS на больших
таблицах, утечь данные через сообщения об ошибке, или нарваться на
side-effect-функции (`pg_read_file`, расширения). Read-only роль не защищает
от запросов на чувствительные поля, которые судья как раз должен отлавливать.

Эталонный датасет уже содержит ожидаемые SQL-запросы, и Execution Accuracy
можно мерить оффлайн через сравнение result-set'ов на синтетической БД
(`make db-seed`), без подключения к продовой.

## Decision

Система **не исполняет** сгенерированный SQL в рантайме. Ответ пайплайна —
текст SQL, audit-лог и решение об одобрении. Execution Accuracy замеряется
отдельным процессом `case3 eval` на изолированном PostgreSQL в Docker.

## Alternatives considered

- **Sandbox-исполнение read-only ролью.** Отклонено: read-only роль не
  предотвращает раскрытие ПДн через корректный SELECT — судья всё равно
  обязан анализировать запрос статически. Дополнительная инфраструктура
  (изолированный кластер, тайм-ауты, kill-switch) выходит за рамки MVP.
- **Dry-run через `EXPLAIN`.** Отклонено: `EXPLAIN` не ловит семантические
  риски (доступ к чувствительным колонкам, отсутствие пагинации); даёт
  ложное чувство безопасности.

## Consequences

- Метрика Execution Accuracy замеряется только в оффлайн-режиме (`case3 eval`
  + локальный Postgres), не в продакшен-цикле.
- Судья обязан полностью полагаться на статический и семантический анализ
  текста SQL — нет фолбэка «выполним и посмотрим».
- В будущем сюда можно навесить sandbox-проверку как опциональный слой, не
  меняя контрактов `SQLSecuritySystem`.
