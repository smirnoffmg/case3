# 5. Генератор: prompt + BM25 RAG, без fine-tuning

Date: 2026-05-20

## Status

Accepted

## Context

Тестовая БД содержит ~60 таблиц; полный DDL — десятки тысяч токенов. В
лоб засовывать в LLM нельзя: бьёт в контекстный лимит локальных моделей,
дорого для облачных, заставляет модель удерживать массу нерелевантного.

Доступные варианты, чтобы привязать модель к реальной схеме:

1. **Fine-tuning** на парах NL → SQL для конкретной схемы.
2. **Retrieval-Augmented Generation:** на каждый запрос отбирать релевантные
   таблицы из индекса и инжектить их DDL в промпт.
3. **Полный DDL в системный промпт.**

## Decision

Используем **Prompt + RAG (BM25)**:

- `schema_index/build_schema_index.py` парсит DDL в `schema.json`
  (таблицы, колонки, комментарии, FK-рёбра).
- `schema_index/retriever.py` строит BM25-индекс по
  `table_name + columns + comments`. На каждую задачу возвращает top-K
  таблиц (`RETRIEVER_TOP_K=8` по умолчанию).
- `generator/prompt_rag.py` собирает финальный промпт:
  системные инструкции + отобранные таблицы (DDL-выжимка) + few-shot
  примеры из `data/examples/few_shot.yaml` + текст задачи + (на повторных
  итерациях) уроки из `FeedbackMemory`.
- `LLM_TEMPERATURE=0.0` — детерминированная генерация.

LLM подключается через единый `get_llm_client()` фабричный метод,
поддерживающий три провайдера: Ollama (локально, `qwen2.5:7b` по
умолчанию), OpenAI-совместимые API, Claude (Anthropic).

## Alternatives considered

- **Fine-tuning под схему PSB.** Отклонено для MVP:
  - нет размеченного корпуса достаточного размера (наш `tasks.jsonl` —
    87 пар, мало для дообучения);
  - при изменении схемы (новая таблица/колонка) модель нужно
    переобучать — это плохо для прода с эволюционирующей БД;
  - результаты обычно дороже и хуже воспроизводимы, чем prompt+RAG на
    современных моделях.
- **Полный DDL в промпт.** Отклонено: 60+ таблиц не помещаются в
  контекст локальных моделей; на облачных — лишние токены за
  каждую итерацию.
- **Эмбеддинги (FAISS / dense retrieval).** Отклонено для MVP: BM25
  даёт хорошее качество на коротких структурированных доках
  (имя_таблицы + комментарий) и не требует отдельной модели/индекса в
  памяти. Можно докинуть как улучшение, если BM25 начнёт промахиваться
  на конкретных доменах.
- **Single-LLM (один провайдер).** Отклонено: разные среды требуют разных
  моделей (Ollama для разработки без интернета, Claude для качества,
  GreenData proxy в проде кейса) — фабрика даёт переключение без правок
  кода.

## Consequences

- Качество генерации зависит от качества BM25-ретривера. Если запрос на
  одном языке (русский), а индекс на другом (английские
  идентификаторы вроде `sys_employee`), retrieval промахивается. Это
  требует токенизации идентификаторов по `_` и/или словаря синонимов
  (см. TO_FIX #10).
- Контракт `SQLGenerator` остаётся stateless — все улучшения retrieval
  изолированы в `schema_index/`.
- При смене провайдера LLM не меняется ни код пайплайна, ни промпт; в
  `.env` достаточно переключить `LLM_PROVIDER`.
- `temperature=0.0` фиксирует ответы при том же входе, что критично для
  `case3 eval` и регрессионных метрик.
