# 3. Гибридный аудитор: статический анализ + LLM-судья

Date: 2026-05-20

## Status

Accepted

## Context

Сгенерированный SQL должен проверяться на десяток классов уязвимостей:
SQL-инъекции (classic, UNION, time-based), DML без WHERE, прямой доступ к
ПДн, SELECT *, отсутствие LIMIT, privilege escalation, небезопасный
PL/pgSQL, несоответствие SQL поставленной задаче. Эти классы делятся на две
группы:

1. **Синтаксические** — детектируются регулярками и AST (sqlglot):
   `SELECT *`, `DELETE` без `WHERE`, `pg_sleep(...)`, `GRANT`/`REVOKE`,
   `EXECUTE` с конкатенацией. Здесь LLM не нужен и даже вреден:
   недетерминирован, тратит токены, может пропустить очевидное.
2. **Семантические** — требуют понимания задачи: SQL не отвечает на запрос
   пользователя, доступ к чувствительному полю замаскирован (`u.e AS x`),
   логика обхода фильтров. Сюда статика не дотягивается.

## Decision

Аудитор — **гибрид из двух всегда включённых слоёв**:

- `StaticAnalyzer` (sqlglot + regex) ловит синтаксические классы и
  чувствительные поля по схеме индекса.
- `LLMJudge` получает SQL + задачу + краткую выжимку схемы и оценивает
  семантику.

Находки сливаются в `HybridAuditor._merge_findings` по ключу
`(vuln_class, line_hint)` — дубль между статикой и LLM не порождает двух
записей в audit-логе.

## Alternatives considered

- **Только LLM-судья.** Отклонено: нестабильно ловит инъекции с явным
  паттерном (`pg_sleep`, `' || var`), а пропуск этих классов — самая
  дорогая ошибка системы (риск 8.0+).
- **Только статика.** Отклонено: не понимает соответствие SQL задаче
  («покажи 10 сотрудников» vs. сгенерированный `SELECT COUNT(*) ...`) и
  плохо ловит обфусцированные обращения к ПДн.
- **LLM как фолбэк после статики.** Отклонено: статика и LLM могут найти
  разные классы на одном SQL; ранний выход скрывает уязвимости.

## Consequences

- Каждый аудит делает **минимум один LLM-вызов**. Бюджет на одну итерацию —
  ~1–2 сек на локальной Ollama, ~3–5 сек на Claude.
- Контракт `SecurityAuditor` (см. `contracts.py`) допускает плагины: можно
  добавить отдельный детектор как третий слой без изменения политики
  одобрения.
- LLM-судья делается с `temperature=0.0` — аудит детерминирован при том же
  входе, что важно для воспроизводимости метрик.
- Если внешний LLM недоступен, статика продолжает работать
  самостоятельно (`LLMJudge.analyze_safe` ловит исключения).
